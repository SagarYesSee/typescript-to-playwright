Part 1JavaScript

JavaScript, and where it runs

JavaScript is a programming language, and every website uses it. When you click “Add to cart” and the cart number changes without the page reloading, that's JavaScript running inside your browser.

For years, JavaScript could only run inside a browser. Node.js changed that. It's a program you install on your laptop that runs JavaScript files directly, with no browser window. It does the same job for JavaScript that the JVM does for Java.

Inside a browserChrome, Firefox, SafariEach browser has a JavaScript engine built in. It runs the code that comes with web pages.
On your laptopNode.jsRuns JavaScript files from the terminal. Playwright is a Node.js program, so your tests run here.

So when you run a Playwright test, this is what happens:

Your test fileSteps written in TypeScript
→
Node.jsRuns your test code on your laptop
→
PlaywrightTurns each step into a command for the browser
→
The browserOpens pages, clicks and types like a real user
Java comparison

Java code runs on the JVM; JavaScript code runs on Node.js or in a browser. Your Appium tests worked the same way: your Java code sent commands through Appium, and the phone carried them out.

Part 2TypeScript

TypeScript is JavaScript plus types

TypeScript isn't a different language. It's JavaScript with one extra feature, types, which part 8 explains properly. Any JavaScript code is already valid TypeScript. TypeScript only adds rules that your editor checks while you type.

TypeScript = JavaScript + types (rules your editor checks)
JavaScriptThe actual language that runs: variables, functions, loops, objects

Node.js and browsers understand JavaScript, not TypeScript. So before a .ts file runs, a tool strips out the types and leaves plain JavaScript. Part 6 covers those tools.

Why Playwright testers use it
  • Playwright's installer picks TypeScript by default, and most Playwright job posts ask for it.
  • Because of types, VS Code suggests Playwright methods as you type, so you don't have to memorise them.
  • Mistakes get underlined before a test runs, instead of failing later in CI.

Part 5npx

npx: run a tool from your project

Packages like tsx and Playwright are tools you run from the terminal. npm installs them inside your project's node_modules folder, but your terminal doesn't look in there. So typing just tsx hello.ts usually fails with “command not found”.

npx fixes that. It comes with npm, finds the tool inside your project and runs it. If the tool isn't installed, npx offers to download it for that one run.

npxFind this tool in my project and run it
tsxThe tool: runs TypeScript files
hello.tsWhat the tool should work on
npxFind and run a project tool
playwrightThe tool: Playwright
test --headedRun my tests, with the browser visible
Remember it like this

npm installs things. npx runs things.

And npm init playwright@latest?

npm init something runs a project creator called create-something. So this runs create-playwright, which sets up a new Playwright project. @latest means “use the newest version”.

Part 6tsx and tsc

tsx, tsc and Playwright's runner

Node.js runs JavaScript, so something has to remove the types from a .ts file first. Which tool does that depends on what you're doing:

Weeks 1–2tsxRuns a .ts file in one step. It strips the types on the fly and doesn't check them.npx tsx hello.ts

So who checks the types?

VS Code checks live as you type, and npx tsc --noEmit checks the whole project from the terminal or in CI (lesson 10). Neither tsx nor Playwright's runner stops for type errors, so don't skip these checks.

Part 7Values

Values and variables

A value is one piece of data: some text, a number, a yes or no. A variable is a named box that holds a value, so you can use it again by name.

const seals the box once it's filled. let lets you put a new value in later. Start with const, and switch to let only when the value needs to change.

Part 8Types

What types are, properly

A type is the kind of value something is: text, a number, yes or no, a list and so on. The type decides what you're allowed to do with the value. You can make text uppercase, but you can't divide it by 2. You can add two numbers, but a number has no uppercase.

You already use types every day as a tester. Look at a test case sheet:

ColumnWhat's allowedTypeScript type
Test IDAny text, like TC-101string
StepsA number, like 6number
Automated?Yes or noboolean
StatusOnly Pass, Fail or Blocked"Pass" | "Fail" | "Blocked"
TagsA list of textstring[]

A type is that column rule, written in code. If someone types “Passed” into the Status column, a well-built sheet rejects it. TypeScript does the same for your code.

What goes wrong without types

JavaScript: no types
TypeScript: with types
login(12345, "secret_sauce");
Argument of type 'number' is not assignable to parameter of type 'string'.

Five things to know about types

  1. Types are only for checking. They're removed before the code runs, so they never change what your test does. Think of them as a spell-checker for code.
  2. The type goes after the name, with a colon: const steps: number = 6. Java puts it before: int steps = 6.
  3. You often don't have to write them. From const steps = 6, TypeScript works out that steps is a number. This is called inference. Hover over any variable in VS Code to see its type.
  4. Do write them where TypeScript can't guess: function inputs like user: string, and the shape of your test data.
  5. Avoid any. It means “anything goes” and switches checking off for that value.

Lesson 3Types

Basic types, unions and optional fields

There's no int or double, only number. Arrays are written string[] instead of List<String>. Most of the time you don't even write the type, because TypeScript works it out from the value.

Try to break the union and the editor stops you straight away:

Avoid any

Typing something as any turns off checking for that value. It makes errors go away by hiding them, which defeats the point of TypeScript.

Lesson 4Decisions

Conditions, loops and missing values

Programs make decisions with if and repeat steps with loops, just like in Java. Here's day 2's exercise: classify a list of test results.

WriteMeans
=== and !==Equal and not equal. Always use these, never ==.
< > <= >=Less than, greater than, and so on
&&, ||, !And, or, not

When a value might be missing

Test data is often incomplete: a field may be empty, or a search may find nothing. JavaScript has undefined (never set) and null (deliberately empty). TypeScript makes you check before you use a value that might be missing. That check is called narrowing.

Why testers care

A missing value causes the classic “Cannot read properties of undefined” crash in test code. TypeScript underlines the risky line, with a message like “'name' is possibly 'undefined'”, before the test ever runs.

async/await, explained

      
Every Playwright step is await something(). Get this right and Playwright feels easy. Get it wrong and tests become flaky.

    


    
A browser action, like loading a page or clicking a button, takes time. JavaScript doesn't stop and wait. Instead, the action hands you a Promise: a ticket for a result that arrives later.

Under the hood · asked in almost every interview

      
How Playwright talks to the browser

      
This explains why Playwright waits by itself, why tests don't leak into each other, and why tabs, dialogs and network calls are easy to handle. Read it on day 8, and again before interviews.

    


    
The layers, from your code to the screen

    

      
Your testawait page.getByRole("button", { name: "Login" }).click() in login.spec.ts

      
Each call becomes a small message, like “click this locator”

      
Playwright clientThe API you write: page, locator, expect. In TypeScript it runs inside Node.js. The Java, Python and .NET versions send the same messages to a small Node.js driver over a pipe.

      
Hands the message to the server

      
Playwright serverDoes the real work: finds elements, runs the readiness checks, retries, records traces, and translates each command for the browser in use.

      
One long-lived, two-way connection per browser

      

        
ChromiumChrome DevTools Protocol (CDP), the same protocol Chrome's DevTools use

        
FirefoxPlaywright's own protocol, called Juggler, built into a patched Firefox

        
WebKitWebKit's inspector protocol, extended in a patched WebKit

      

      
The browser carries out the command and reports back

      
Browser, contexts and pagesReal clicks, typing and page loads, plus events sent back the moment they happen

    

    
Why Playwright downloads its own browsers
Each Playwright version is built for specific browser versions. Its Firefox and WebKit are patched to add the automation protocol, so it can't drive the normal Firefox or Safari app. For Chromium it uses open-source builds that are a little ahead of Chrome. It can also run your installed Chrome or Edge with the channel option.


    
Letters versus a phone call

    
Classic Selenium WebDriver sends every command as a separate web request to a driver program (chromedriver or geckodriver), which passes it to the browser. It's like posting letters: you send one, wait for the reply, then send the next, and the browser can't write to you first.

    
Playwright keeps one connection open, like a phone call. Commands go one way, and the browser can speak up at any moment: “a new tab opened”, “a dialog appeared”, “this network request started”. That's what makes event waits, network mocking and auto-waiting work so smoothly.

    

      
Selenium: classic WebDriver over HTTP

        

          → POST /session/…/element  (find the button)
          ← element id
          → POST /session/…/element/…/click
          ← ok
          Test → HTTP → chromedriver → browser, for every command
        

      

      
Playwright: one open, two-way connection

        

          → click(button “Login”)
          ← event: request POST /api/login
          ← event: page navigated
          ← click done
          Events arrive without being asked for
        

      

    

    
To be fair to Selenium: version 4 is adding WebDriver BiDi, a newer two-way standard that brings events like console logs and network interception to Selenium as well.


    
What happens in one click

    

    
    
      
  1. Send. The client sends a “click” message that carries the locator, not an element it already found.
    2. 
      
  2. Find it now. The server looks up the locator on the current page. It must match exactly one element. Two matches is an error (strict mode), not a guess.
    3. 
      
  3. Check it's ready. Visible, stable (in the same place for two animation frames), receiving events (nothing covering it) and enabled.
    4. 
      
  4. Wait if it isn't. If a check fails, Playwright re-checks until it passes or the timeout ends. Then you get a TimeoutError with a log of what it was waiting for.
    5. 
      
  5. Scroll. It scrolls the element into view if needed.
    6. 
      
  6. Click like a person. It sends real mouse move, press and release events at the centre of the element through the protocol.
    7. 
      
  7. Reply. The browser confirms, the Promise resolves, your await finishes and the next line runs.
    8. 
    

    
Compared with Selenium
In Selenium you find the element first and keep a reference to it. If the page re-renders, that reference breaks with a StaleElementReferenceException. A Playwright locator is looked up fresh at step 2 every time, so it can't go stale.


    
Browser, context and page

    

      BrowserOne Chromium, Firefox or WebKit process
      

        
Context for test 1Its own cookies, storage and login
Page (tab)Pop-up tab

        
Context for test 2Separate cookies, storage and login
Page (tab)

      

    

    
Starting a whole browser is slow, but a context is cheap and quick to create. So Playwright Test gives every test its own fresh context, with no cookies or logins left over from the test before. It's like opening a new incognito window for each test without restarting the browser.


    
How this design reduces flaky tests

    

      
Common cause of flaky testsWhat Playwright does about it

      
        
Clicking before the element is readyReadiness checks before every action

        
Checking text before it has loadedWeb-first assertions retry until they pass

        
Stale element referencesLocators are looked up fresh for every action

        
One test's login or cart leaking into the nextA fresh browser context for every test

        
Missing a pop-up, dialog or API callEvents arrive over the open connection, and you can wait for them

        
“It failed in CI and I can't tell why”Traces record every step with the DOM, network and console, so you can replay it

Chapter 4Finding elements

      

        
Locators

        
A locator describes how to find an element. Playwright looks it up again every time you use it, and an action fails if it matches more than one element (strict mode). Prefer locators based on what a user sees.

        

          
LocatorBest for

          
            
getByRoleButtons, links, headings, checkboxes, rows, menu items. Try this first.

            
getByLabelForm fields that have a label

            
getByPlaceholderInputs with placeholder text but no label

            
getByTextNon-interactive text, messages and headings without a role

            
getByAltText / getByTitleImages, and elements with a title attribute

            
getByTestIdElements with no stable visible text. Uses data-testid by default.

            
locator("css or xpath")Last resort

Copying a long CSS path or XPath from DevTools, like #root > div > div:nth-child(3) button. It breaks as soon as the layout changes. If you see “strict mode violation … resolved to 6 elements”, make the locator more specific with a name or filter rather than reaching for nth().

Chapter 5Doing things

      

        
Actions and interactions

        
Every action waits for the element to be ready first (chapter 6). The lines below are examples; the button and field names are made up unless they're Sauce Demo's.

        

        
New tabs, dialogs, file choosers, downloads and iframes follow one pattern: start waiting for the event, then act. See Interaction labs.

Using fill() on a search box that suggests results as you type. fill() sets the whole value at once, so the suggestions may never appear. Use pressSequentially() there. And avoid click({ force: true }): it skips the readiness checks and hides real problems.

Chapter 6Waiting

      

        
Auto-waiting and timeouts

        
Before acting, Playwright checks the element is ready: for a click, that it matches one element and is visible, stable, receiving events and enabled. It keeps re-checking until a timeout. These are the timeouts you'll meet:

        

          
TimeoutDefaultChange it with

          
            
Each test, including beforeEach and fixtures30 secondstimeout: 60_000 in config, or test.setTimeout()

            
Each expect assertion5 secondsexpect: { timeout: 10_000 }, or { timeout } on one assertion

            
Each action, like clickNo limit of its own (the test timeout still applies)use: { actionTimeout }, or { timeout } on one action

            
Each navigation, like gotoNo limit of its ownuse: { navigationTimeout }

            
The whole runNoneglobalTimeout: 3_600_000

          
        

        

        
Common mistake
await page.waitForTimeout(5000). It's either too long, which slows every run, or too short, which makes the test flaky. Also, waiting only for a spinner to disappear can pass before loading has even started: assert the final content instead.

        
Docs: Auto-waiting ↗ · Timeouts ↗

      

    


    

      
Chapter 7Checking

      

        
Assertions

        
Assertions on a page or locator retry until they pass or time out. Always await them.

        

        
Common mistake
expect(await locator.textContent()).toBe("2"). It reads the text once, so it fails if the badge updates a moment later. Use await expect(locator).toHaveText("2"), which retries.

Chapter 10Isolation

      

        
Contexts, pages and isolation

        
A browser holds contexts; a context holds pages (tabs). Each test gets its own context, so cookies and logins never leak between tests. For two users in one test, create two contexts.

        

        
The diagram and the reasoning are in How it works.

        
Common mistake
Using one context for two different users. They share cookies, so the second login quietly replaces the first.

Chapter 12Network

      

        
Network interception and mocking

        
page.route() catches requests that match a pattern. You can return your own response, block the request, or let it through. This makes error and empty states easy to test without changing the backend.

        

        
Common mistake
Registering the route after page.goto(). The request has already gone out, so the mock never applies. Set up routes before the action that triggers the request.

Chapter 15Speed

      

        
Parallelism, sharding and speed

        
Playwright runs test files in parallel in separate worker processes. fullyParallel also splits tests inside a file. Sharding splits one run across several machines.

        

        

        
    
          
  • Reuse saved login (chapter 13) instead of logging in through the UI in every test.
    • 
          
  • Create test data through the API (chapter 14), and use the UI only for what you're actually testing.
    • 
          
  • Block heavy third-party requests you don't need (chapter 12).
    • 
          
  • Run a fast smoke tag on every pull request, and the full cross-browser suite on a schedule.
    • 
        

        
Common mistake
Parallel tests sharing one record or one account. They change each other's data and fail at random. Give each test its own data, created with a unique name.

        
Docs: Parallelism ↗ · Sharding ↗

Debugging, tracing and reporting

Re-running a failed test until it passes instead of opening the trace. Find the first step where the page differs from what you expected; that's usually the real cause.

Chapter 19CI/CD

      

        
CI/CD integration

        
The installer can create .github/workflows/playwright.yml. This is that file, with two additions marked: a type check, and a secret passed in from the repo settings.

        

        
    
          
  1. Checks out your code and installs Node.js.
    2. 
          
  2. Installs the exact dependencies from package-lock.json, then type-checks.
    3. 
          
  3. Installs the browsers and their system libraries, and runs the tests.
    4. 
          
  4. Uploads the HTML report even when tests fail. Download it from the run's Artifacts, unzip it, and open it with npx playwright show-report <folder>.
    5.

Uploading reports and traces carelessly. They can contain test credentials, tokens and page data. Keep real secrets in GitHub's repository secrets, and only share artifacts with people who should see that data.

Git 7Watch out

      

        
Beginner mistakes to avoid

        

          
Don't
Upload node_modulesIt's thousands of files that anyone can reinstall with npm ci. Check .gitignore before the first commit.

          
Don't
Commit real passwords or API keysSauce Demo's logins are public, so they're fine. For anything real, use environment variables. Anything you push to a public repo can be seen by everyone, even after you delete it.

          
Avoid
One giant commit at the endSmall daily commits are easier to undo and show your progress.

          
If it happens
First push rejected because GitHub already has a READMERun this once, then push again:git pull origin main --allow-unrelated-histories

Why Playwright over Selenium?

    
This is the most common question. A good answer is balanced: say what Playwright does better, and when you'd still pick Selenium.

    

      
PlaywrightSelenium

      
        
Talks to the browserOne open, two-way connection (CDP, or Playwright's patched protocols for Firefox and WebKit)W3C WebDriver: one HTTP request per command through a driver. WebDriver BiDi is being added.

        
WaitingWaits for elements by itself; assertions retryYou write explicit waits yourself

        
Test isolationA new browser context per test, created in momentsUsually a new browser session or manual cleanup per test

        
Built inTest runner, parallel runs, retries, HTML report, traces, codegen, UI Mode, API testing, network mockingBrowser automation. You add TestNG or JUnit, reporting, Grid and other libraries.

        
BrowsersChromium, Firefox and WebKit builds, plus your installed Chrome and EdgeThe real installed Chrome, Firefox, Edge and Safari, including older versions

        
LanguagesTypeScript/JavaScript, Python, Java, .NETJava, Python, C#, JavaScript, Ruby

        
MobileMobile web through device emulationMobile web, and native apps through Appium, which uses the same WebDriver protocol

        
MaturityReleased in 2020, growing fastAround since 2004, with a huge community and many existing suites

      
    

    
A sample answer in your own words

      
“I've used Selenium and Appium with Java. What I like about Playwright is that it waits for elements by itself and its assertions retry, so I don't need the explicit-wait utilities I had to build in my Appium framework. Every test gets a fresh browser context, so tests don't affect each other, and the runner, HTML report and trace viewer are built in, which makes a failed CI run easy to debug. It also handles new tabs, dialogs and network mocking cleanly because it keeps an open connection to the browser. I'd still choose Selenium where a team needs real Safari or already runs a big Grid, and Appium for native mobile apps.”
